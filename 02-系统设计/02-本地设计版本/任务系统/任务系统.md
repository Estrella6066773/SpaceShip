> 草稿状态：待评审 | 更新：2026-08-06
>

> 「✅ 已确认」条目来自系统描述，已定稿；「⏳ 待确认」条目需决策，见 §8 问题清单。

---

## 1. 系统全景

任务系统统一管理游戏中的任务生命周期、完成判定、激活条件与推进逻辑。任务之间通过前置条件网络连接，支持三种推进形态：

| 形态 | 说明 |
|------|------|
| 线性推进 | 任务 A 完成后解锁任务 B |
| 并行推进 | 多个任务同时进行中，互不阻塞 |
| 分支路线 | 同一组前置任务按「任一完成」逻辑解锁不同后继 |

**版本边界**：当前版本仅实现**主线任务**；支线任务与随机赏金为后续版本扩展内容。本设计为框架级，具体任务内容由策划配置。

任务系统与既有系统的关系：

| 相关系统 | 关系 |
|----------|------|
| 事件系统 | 完成判定与进度推进由关键事件驱动（订阅飞船流 / 货物 / 世界事件源） |
| 货币系统 | 任务完成发放金币 → 货币管理器（见 §5） |
| UI | 任务界面显示可见任务与进度、接受玩家接取操作 |

---

## 2. 任务系统（对象）

### 2.1 系统描述

统一管理游戏中所有类型的任务，负责任务的生命周期、完成判定、激活条件和推进逻辑。

### 2.2 任务（对象）

一个独立的任务实例，包含目标、完成条件和激活条件。多个任务通过前置任务配置形成任务网络。

---

## 3. 数据

### 3.1 任务配置表

由策划配置的任务列表，每个任务节点包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| 任务名称 | 字符串（中文） | 任务显示名 |
| 任务描述 | 字符串（中文） | 目标描述，任务界面展示 |
| 目标类型 | 枚举 | 任务目标类型（见 §3.2） |
| 目标参数 | 按类型 | 目标数量 / 目标对象（见 §3.2） |
| 激活条件 | 结构 | 前置任务组 + 逻辑（见 §3.3） |
| 完成条件 | 配置 | 目标达成即完成（本版单目标，见 §3.4） |
| 奖励规则 | 结构列表 | 完成时发放的奖励类型和数量（见 §3.5） |
| 所属任务组 | 引用 | 归属的任务组（见 §3.6） |

> 配置实现为 ScriptableObject（`QuestConfig`），任务间前置关系通过**资产引用**连接，遵循项目数据驱动与显式装配规范。

### 3.2 任务目标

目标由「目标类型 + 目标参数」构成。本版目标类型与既有事件源对齐，由事件驱动推进：

| 目标类型 | 参数 | 推进事件 | 说明 |
|----------|------|----------|------|
| 摧毁敌舰 `KillEnemies` | 数量 | `ShipDestroyedEvent` | 玩家击毁敌方飞船 |
| 收集货物 `CollectCargo` | 货物类别 + 数量 | `CargoChangedEvent` | 玩家持有某类别货物达量 |
| 到达目的地 `ReachDestination` | 目的地名称 | `ExpeditionCompletedEvent` | 降落 / 返航到指定地点 |
| 存活天数 `SurviveDays` | 天数 | `DayEndedEvent` | 累计存活天数 |

> ⏳ **决策 Q1**：本版目标类型集合是否采用上表四类？是否还有缺失（如交付货物）？
> ⏳ **决策 Q2**：本版每任务是否仅支持**单目标**（推荐：是，多目标组合留待支线 / 赏金版本）？

### 3.3 激活条件

激活条件为一组前置任务的完成状态组合，支持两种逻辑：

| 字段 | 说明 |
|------|------|
| 前置任务列表 | 引用若干前置任务节点 |
| 逻辑 | `全部完成 All` / `任一完成 Any` |
| 无前置 | 前置列表为空 = 起始任务，系统初始化时自动进入待接取 |

示例（线性 + 分支）：

```
主线·序章（起始，无前置）
 ├── 全部完成 → 主线·第一章
 ├── 全部完成 → 主线·第二章（并行）
 └── 任一完成（并行支线 a / b）→ 主线·第三章（分支）
```

### 3.4 完成条件

完成条件由策划在配置中定义。本版主线任务采用**目标达成即完成**的最简模型：单目标达成 → 任务完成 → 发放奖励 → 触发新一轮激活检测。

> ⏳ **决策 Q3**：本版是否只需「单目标达成即完成」？多阶段 / 多目标组合是否留待后续版本？

### 3.5 奖励规则

奖励规则定义任务完成时发放的奖励类型和数量：

| 字段 | 类型 | 说明 |
|------|------|------|
| 奖励类型 | 枚举 | 奖励类型（本版金币；扩展货物 / 模块） |
| 奖励数量 | 整数 | 发放数量 |

**本版仅实现金币奖励**：任务完成 → 货币管理器增加金币 → 广播金币变更。货物、模块奖励留待后续版本。

> ✅ **决策 D-8**：完成任务的金币走货币管理器发放（与《货币与商店系统》一致，解决该文档 Q20）。

### 3.6 任务组

策划可将多个任务归入同一任务组，用于管理同一剧情线或同一区域的任务集合：

| 字段 | 类型 | 说明 |
|------|------|------|
| 组名 | 字符串（中文） | 任务组显示名 |
| 任务列表 | 引用列表 | 归属于该组的任务 |

- 任务组之间**互不影响**（组 A 的推进不阻塞组 B）
- 同一任务组内的任务按激活条件网络推进
- 任务归属采用**「任务引用组」**：任务节点上配置所属组

> ⏳ **决策 Q4**：任务归属采用「任务引用组」还是「组持有任务列表」？（推荐：任务引用组，避免双向引用，配置直观）

### 3.7 任务状态

| 状态 | 说明 |
|------|------|
| 未激活 `Inactive` | 激活条件尚未满足，任务不可见 |
| 待接取 `Available` | 激活条件已满足，任务界面显示，可被接取 |
| 进行中 `InProgress` | 玩家已接取任务，正在执行 |
| 已完成 `Completed` | 目标已达成，奖励已发放 |

状态流转（单向）：

```
未激活 ──激活──▶ 待接取 ──接取──▶ 进行中 ──完成──▶ 已完成
```

主线任务无失败状态。

## 4. 状态与行为

### 4.1 任务激活

系统在**任务状态变更**时检测所有未激活任务的激活条件：

- 条件满足 → 状态切换为待接取，在任务界面显示
- 检测时机：系统初始化、任意任务完成、任务组状态变更
- 完成一个任务可能激活**多个**新任务（扇出）

### 4.2 任务接取

玩家在任务界面选择待接取任务并确认接取：

- 状态切换为进行中
- 玩家可同时持有多个进行中任务（无数量上限）
- 接取操作为 UI → 任务系统的**命令调用**（同步、有结果）

### 4.3 完成判定

系统在**关键事件发生**时检测所有进行中任务的目标是否达成：

1. 订阅事件源（`ShipDestroyedEvent` / `CargoChangedEvent` / `ExpeditionCompletedEvent` / `DayEndedEvent`）
2. 更新对应任务的目标进度
3. 目标达成 → 状态切换为已完成 → 发放奖励 → 触发新一轮任务激活检测

### 4.4 任务查询

提供只读查询接口，供 UI 系统在任务界面调用：

| 查询 | 返回 |
|------|------|
| 可见任务状态列表 | 待接取 / 进行中 / 已完成任务及其状态 |
| 各任务目标描述 | 目标类型、参数的人类可读描述 |
| 完成进度 | 每个目标的当前值 / 目标值 |

## 5. 事件契约

| 事件 | 触发时机 | 载荷关键字段 | 状态 |
|------|----------|--------------|------|
| `QuestStateChanged` | 任务状态变更 | 任务、旧状态、新状态 | ✅ 已确认 |
| `QuestProgressChanged` | 进行中任务目标进度变化 | 任务、目标索引、当前值、目标值 | ✅ 已确认 |
| `QuestAccepted` | 任务接取成功 | 任务 | ✅ 已确认 |
| `QuestCompleted` | 任务完成、奖励已发放 | 任务、奖励明细 | ✅ 已确认 |

- 事件源为场景实例 `QuestEventSource`，遵循事件-订阅规范（不引用订阅者、载荷 `readonly struct`、只广播事实）
- UI 订阅事件刷新任务界面
- 金币变更**复用**货币系统的 `CoinsChanged`，任务系统不重复广播

## 6. 架构与通信

```
QuestEventSource（场景实例，广播任务事件）
    ▲ 订阅（完成判定 / 进度推进）
    │
QuestSystem（System）──▶ 货币管理器（发放金币，Command）
    │
    ├── QuestConfig / QuestGroupConfig（ScriptableObject，静态配置）
    └── QuestInstance（运行时状态：状态 + 进度）

任务界面（UI）──查询──▶ QuestSystem（可见任务 / 描述 / 进度）
任务界面（UI）──接取──▶ QuestSystem（AcceptQuest，Command）
任务界面（UI）◀──订阅── QuestEventSource
```

| 通信 | 形式 | 方向 |
|------|------|------|
| 关键事件 → 进度推进 | 事件订阅 | QuestSystem → 事件源 |
| 奖励发放 | Command | QuestSystem → 货币管理器 |
| 任务状态广播 | 事件广播 | QuestSystem → QuestEventSource → UI |
| 可见任务 / 进度查询 | Query | UI → QuestSystem |
| 接取任务 | Command | UI → QuestSystem |

### Q1 目标类型集合

**所处环境**

系统描述只写了「任务目标类型」由策划在配置中定义，没有给出具体类型清单。而本系统的完成判定约束是「在关键事件发生时检测」，这意味着每个目标类型必须能映射到项目里已有的**事件源**，事件驱动推进，不采用轮询（符合事件-订阅规范与零堆分配约定）。当前可用的事件源清单见《事件系统设计》：飞船流（`ShipDestroyedEvent` / `DayEndedEvent` / `ExpeditionCompletedEvent`）、货物流（`CargoChangedEvent`）、模块流（`ModuleDestroyedEvent` / `CoreExplodedEvent`）、雷达流（`RadarScanEvent`）。

**产生原因**

本版（仅主线任务）应开放哪些目标类型？是否采用建议的四类：摧毁敌舰、收集货物、到达目的地、存活天数？

**导致后果**

- 若选得太少（如只有「摧毁敌舰」），主线表达受限，策划无法配置「收集 X 货物」「抵达 X 地点」这类引导性任务，主线会退化成纯战斗线。
- 若选得太多，每个类型都要新增事件订阅、进度维护与查询展示代码，实现成本线性上升；其中「摧毁敌舰」还需区分敌我（`ShipDestroyedEvent` 载荷含 `ShipAssembly`，需按阵营判定）。
- 若选了一个**没有事件支撑**的目标（如「交付货物」——目前货物只有拾取与消耗，无「交付」行为），就必须新增事件源或退回轮询，违反事件驱动约束，成本最高。
- 建议四类正好覆盖项目的四个核心循环要素：战斗（摧毁敌舰）、探索收获（收集货物）、探索目标（到达目的地）、生存时间（存活天数），均直接复用既有事件，无需新增事件。

**解决建议**：本版采用四类（摧毁敌舰 / 收集货物 / 到达目的地 / 存活天数），与既有事件源一一对齐；若主线草案需要第五类目标，评审时直接补进表内并说明对应事件。

### Q2 单目标 or 多目标

**所处环境**

系统描述未限定一个任务可包含几个目标；「完成条件由策划在配置中定义」的表述既允许单目标也允许多目标。但数据模型上，目标数量决定了运行时 `QuestInstance` 的进度结构：单目标用「一个当前值/目标值」，多目标要用「目标列表，每项独立进度」。UI 的进度展示也随目标数量变化（单行进度 vs 每目标一行）。后续支线 / 赏金任务通常天然需要多目标（如「收集 5 食物 + 击败 2 敌舰」）。

**产生原因**

本版主线任务每任务支持单目标还是多目标？

**导致后果**

- 若**现在实现多目标**：进度结构、完成判定（全部目标达成才完成）、UI 展示都要一次做全，实现成本高；而主线任务通常「做一件事」即可完成，本版很可能用不上。
- 若**现在就定为单目标且结构写死**（如进度字段为单值）：后续版本加多目标要重构 `QuestInstance` 数据与 UI，扩展成本转嫁到后期。
- 折中：**数据结构按「目标列表」设计**（列表可只有一个元素），本版每任务只配一个目标。这样后续加多目标只改配置与判定循环，不改数据结构。

**解决建议**：数据结构预留目标列表，本版每任务仅配置单目标；多目标组合留待支线 / 赏金版本启用。

### Q3 完成条件模型

**所处环境**

系统描述写明「完成条件由策划在配置中定义」，说明完成判定不应硬编码，而应是可配置规则；同时「完成判定」又是系统的核心行为。激活条件网络只能表达「前置任务完成」这种**任务间**关系，无法表达**任务内部**的先后阶段（如「先去 A 地，再回 B 地」）。本版主线以线性引导为主，多数任务「目标一达成即完成」即可覆盖。

**产生原因**

本版是否需要比「目标达成即完成」更复杂的完成条件模型（如任务内多阶段顺序推进）？

**导致后果**

- 最简模型（目标达成即完成）：实现快，主线够用；任务内多阶段用「拆成多个串联任务」表达（A 地任务 → B 地任务），代价是任务节点变多，但任务网络本就支持线性串联。
- 阶段模型（任务内分阶段）：能表达「同一任务内先到 A 再到 B」，但需新增「阶段」数据结构、阶段间推进判定与 UI 阶段显示，本版成本高。
- 若现在不选阶段模型，后续启用时需扩展 `QuestInstance` 结构；但阶段通常可被「拆任务」绕过，风险可控。

**解决建议**：本版采用最简模型「目标达成即完成」；任务内多阶段一律用任务网络拆成串联任务表达，阶段模型留待后续版本（若真有需求再评估）。

### Q4 任务归属方式

**所处环境**

系统描述定义任务组为「多个任务的集合」，用于管理同一剧情线或同一区域；任务组之间互不影响。实现上有两种装配方向：**任务引用组**（`QuestConfig` 上配置所属组）或**组持有任务**（`QuestGroupConfig` 上配置任务列表）。项目规范要求显式组合优先、避免循环引用。

**产生原因**

任务与任务组的从属关系由哪一端持有引用？

**导致后果**

- 任务引用组：策划配置单个任务时顺手选组，任务不会「忘挂进组」；一个任务可属多组（若未来允许，零成本）；代价是「某组有哪些任务」需运行时遍历任务集。
- 组持有列表：组内任务一目了然，方便按组批量编辑；代价是若允许一个任务属多组，需在多个组的列表间维护一致性；且任务易遗漏挂载。系统描述未限制一个任务只能属一组，多对多场景下「组持有列表」的一致性维护成本明显更高。

**解决建议**：采用「任务引用组」——`QuestConfig` 配 `所属任务组` 字段；UI 按任务组的组名做展示分组（任务遍历时按组归类）。避免双向引用，配置直观。

### Q5 任务状态是否随存档持久化

**所处环境**

项目已有单存档服务（`GameSaveService` + `SaveData`，当前 `schemaVersion = 3`），持久化金币、欠账、模块库存、货物库存与仓库。其中**金币是跨局、跨会话的永久资源**（决策 C-1）。而系统描述没有说明任务状态（激活进度、进行中进度）是否跨局保留。主线剧情通常属于「长期进度」——若每次开局都从序章重置，主线推进就失去意义；但任务状态若不入存档，又会和「金币已入存档」产生冲突。

**产生原因**

任务运行时状态（各任务状态、目标进度）是否写入存档并跨局恢复？

**导致后果**

- 若**不持久化**：每次开局任务全部回到未激活，主线永远从序章开始；更严重的是——金币已跨局保留，而「已完成」状态不保留，重开会再次出现待接取的序章任务，**玩家可反复完成并重复领取金币奖励**，造成经济系统漏洞。这不是「可选项」，而是必须与金币生命周期对齐的硬约束。
- 若**持久化**：需在 `SaveData` 增加任务状态条目（任务 ID + 状态 + 进度），`schemaVersion` 升为 4；任务系统启动时从存档恢复，任务完成后标记并落档。成本是一次数据结构扩展 + 存档版本迁移，但能同时解决「主线推进保留」与「奖励防重复领取」。

**解决建议**：任务状态随存档持久化，与金币生命周期对齐（奖励已入存档，任务状态也必须入存档）；写入时机与金币一致（变更即存、退出前存）。这是本版应尽早定稿的问题，因为它直接决定任务系统是否要接入 `GameSaveService` 的启动/保存流程。

---

### Q6 主线任务内容

**所处环境**

系统描述声明「当前版本仅实现主线任务」，但未给出主线任务的具体内容；设定文档虽有剧情素材（如 A 站受命前往巨企 N 管辖区制造骚乱、驾驶员视角的「打捞回收」），但那是**世界观设定**，不是**可配置的任务列表**。本设计定位为框架级，任务内容由策划配置。

**产生原因**

主线任务的具体剧情线（任务清单、顺序、分支点）由谁何时提供？本版是「框架先行 + 占位任务」还是「内容先行」？

**导致后果**

- 框架先行：先实现系统与配置表，用占位任务（如「摧毁 1 艘敌舰」）验证全流程；主线内容后续由策划填充。风险是配置表字段可能与最终主线需求不匹配，需要一次字段迭代。
- 内容先行：先定主线剧情草案（按设定素材规划任务节点与前置网络），据此校验配置表字段是否够用，再实现系统。成本是要先做一轮主线剧情设计，但能避免字段返工。

**解决建议**：框架先行，实现期用占位任务打通流程；同时起草一份主线任务草案（3~5 个节点即可）用于**校验配置表字段覆盖度**，发现缺口当场回填本设计，不等策划正式产出。

---

### Q7 奖励类型扩展

**所处环境**

系统描述：「奖励规则定义任务完成时发放的奖励类型和数量」——未限定奖励类型。金币已定稿走货币管理器（决策 D-8）。货物 / 模块奖励则面临落点歧义：项目已区分**飞船货舱**（`ShipCargoHold`，局内装载、随飞船损毁丢失）与**仓库**（`WarehouseDefinition`，局外自由格背包、随存档跨局保留）。任务奖励发到哪一侧，直接决定奖励的存续语义。

**产生原因**

本版是否只实现金币奖励？货物 / 模块奖励的发放路径（货舱 or 仓库）如何定？

**导致后果**

- 本版只做金币：不触碰落点问题，与货币系统对接成本最低，主线「给金币引导玩家消费」的循环即可成立。
- 若做货物奖励：必须定落点——发到局内货舱，飞船损毁即丢失，适合即时消耗型奖励；发到局外仓库，跨局保留，适合长期资源型奖励。落点错误会导致奖励「该丢的没丢、该留的没留」。
- 若做模块奖励：还需与车间 / 仓库系统对齐（模块入库存还是直接装配），依赖后续决策。
- 系统描述未声明本版含金币以外的奖励，过早扩展会把「落点决策」提前到未成熟的阶段。

**解决建议**：本版仅实现金币奖励；奖励类型枚举预留「货物 / 模块」占位，落点规则留待货币文档与仓库系统定稿后一并设计，并在 §3.5 增补对应字段。
