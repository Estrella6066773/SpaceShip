> 草稿状态：待评审 | 更新：2026-08-06
>
> 本文档为**任务系统**的设计草稿。任务系统统一管理游戏中所有类型的任务。
> 「✅ 已确认」条目来自系统描述，已定稿；「⏳ 待确认」条目需决策，见 §8 问题清单。
>

## 1. 系统全景

任务系统统一管理游戏中的任务生命周期、完成判定、激活条件与推进逻辑。任务之间通过前置条件网络连接，支持三种推进形态：

| 形态 | 说明 |
|------|------|
| 线性推进 | 任务 A 完成后解锁任务 B |
| 并行推进 | 多个任务同时进行中，互不阻塞 |
| 分支路线 | 同一组前置任务按「任一完成」逻辑解锁不同后继 |

**版本边界**：当前版本仅实现**主线任务**；支线任务与随机赏金为后续版本扩展内容。本设计为框架级，具体任务内容由策划配置。

任务系统与既有系统的关系：

| 相关系统 | 关系 |
|----------|------|
| 事件系统 | 完成判定与进度推进由关键事件驱动（订阅飞船流 / 货物 / 世界事件源） |
| 货币系统 | 任务完成发放金币 → 货币管理器（见 §5） |
| UI | 任务界面显示可见任务与进度、接受玩家接取操作 |

---

## 2. 任务系统（对象）

### 2.1 系统描述

统一管理游戏中所有类型的任务，负责任务的生命周期、完成判定、激活条件和推进逻辑。

### 2.2 任务（对象）

一个独立的任务实例，包含目标、完成条件和激活条件。多个任务通过前置任务配置形成任务网络。

---

## 3. 数据

### 3.1 任务配置表

由策划配置的任务列表，每个任务节点包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| 任务名称 | 字符串（中文） | 任务显示名 |
| 任务描述 | 字符串（中文） | 目标描述，任务界面展示 |
| 目标类型 | 枚举 | 任务目标类型（见 §3.2） |
| 目标参数 | 按类型 | 目标数量 / 目标对象（见 §3.2） |
| 激活条件 | 结构 | 前置任务组 + 逻辑（见 §3.3） |
| 完成条件 | 配置 | 目标达成即完成（本版单目标，见 §3.4） |
| 奖励规则 | 结构列表 | 完成时发放的奖励类型和数量（见 §3.5） |
| 所属任务组 | 引用 | 归属的任务组（见 §3.6） |

> 配置实现为 ScriptableObject（`QuestConfig`），任务间前置关系通过**资产引用**连接，遵循项目数据驱动与显式装配规范。

### 3.2 任务目标

目标由「目标类型 + 目标参数」构成。本版目标类型与既有事件源对齐，由事件驱动推进：

| 目标类型 | 参数 | 推进事件 | 说明 |
|----------|------|----------|------|
| 摧毁敌舰 `KillEnemies` | 数量 | `ShipDestroyedEvent` | 玩家击毁敌方飞船 |
| 收集货物 `CollectCargo` | 货物类别 + 数量 | `CargoChangedEvent` | 玩家持有某类别货物达量 |
| 到达目的地 `ReachDestination` | 目的地名称 | `ExpeditionCompletedEvent` | 降落 / 返航到指定地点 |
| 存活天数 `SurviveDays` | 天数 | `DayEndedEvent` | 累计存活天数 |

> ⏳ **决策 Q1**：本版目标类型集合是否采用上表四类？是否还有缺失（如交付货物）？详见 §8.1。
> ⏳ **决策 Q2**：本版每任务是否仅支持**单目标**（推荐：是，多目标组合留待支线 / 赏金版本）？详见 §8.2。

### 3.3 激活条件

激活条件为一组前置任务的完成状态组合，支持两种逻辑：

| 字段 | 说明 |
|------|------|
| 前置任务列表 | 引用若干前置任务节点 |
| 逻辑 | `全部完成 All` / `任一完成 Any` |
| 无前置 | 前置列表为空 = 起始任务，系统初始化时自动进入待接取 |

示例（线性 + 分支）：

```
主线·序章（起始，无前置）
 ├── 全部完成 → 主线·第一章
 ├── 全部完成 → 主线·第二章（并行）
 └── 任一完成（并行支线 a / b）→ 主线·第三章（分支）
```

### 3.4 完成条件

完成条件由策划在配置中定义。本版主线任务采用**目标达成即完成**的最简模型：单目标达成 → 任务完成 → 发放奖励 → 触发新一轮激活检测。

> ⏳ **决策 Q3**：本版是否只需「单目标达成即完成」？多阶段 / 多目标组合是否留待后续版本？详见 §8.3。

### 3.5 奖励规则

奖励规则定义任务完成时发放的奖励类型和数量：

| 字段 | 类型 | 说明 |
|------|------|------|
| 奖励类型 | 枚举 | 奖励类型（本版金币；扩展货物 / 模块） |
| 奖励数量 | 整数 | 发放数量 |

**本版仅实现金币奖励**：任务完成 → 货币管理器增加金币 → 广播金币变更。货物、模块奖励留待后续版本。

> ✅ **决策 D-8**：完成任务的金币走货币管理器发放（与《货币与商店系统》一致，解决该文档 Q20）。

### 3.6 任务组

策划可将多个任务归入同一任务组，用于管理同一剧情线或同一区域的任务集合：

| 字段 | 类型 | 说明 |
|------|------|------|
| 组名 | 字符串（中文） | 任务组显示名 |
| 任务列表 | 引用列表 | 归属于该组的任务 |

- 任务组之间**互不影响**（组 A 的推进不阻塞组 B）
- 同一任务组内的任务按激活条件网络推进
- 任务归属采用**「任务引用组」**：任务节点上配置所属组

> ⏳ **决策 Q4**：任务归属采用「任务引用组」还是「组持有任务列表」？（推荐：任务引用组，避免双向引用，配置直观）详见 §8.4。

### 3.7 任务状态

| 状态 | 说明 |
|------|------|
| 未激活 `Inactive` | 激活条件尚未满足，任务不可见 |
| 待接取 `Available` | 激活条件已满足，任务界面显示，可被接取 |
| 进行中 `InProgress` | 玩家已接取任务，正在执行 |
| 已完成 `Completed` | 目标已达成，奖励已发放 |

状态流转（单向）：

```
未激活 ──激活──▶ 待接取 ──接取──▶ 进行中 ──完成──▶ 已完成
```

主线任务无失败状态。

## 4. 状态与行为

### 4.1 任务激活

系统在**任务状态变更**时检测所有未激活任务的激活条件：

- 条件满足 → 状态切换为待接取，在任务界面显示
- 检测时机：系统初始化、任意任务完成、任务组状态变更
- 完成一个任务可能激活**多个**新任务（扇出）

### 4.2 任务接取

玩家在任务界面选择待接取任务并确认接取：

- 状态切换为进行中
- 玩家可同时持有多个进行中任务（无数量上限）
- 接取操作为 UI → 任务系统的**命令调用**（同步、有结果）

### 4.3 完成判定

系统在**关键事件发生**时检测所有进行中任务的目标是否达成：

1. 订阅事件源（`ShipDestroyedEvent` / `CargoChangedEvent` / `ExpeditionCompletedEvent` / `DayEndedEvent`）
2. 更新对应任务的目标进度
3. 目标达成 → 状态切换为已完成 → 发放奖励 → 触发新一轮任务激活检测

### 4.4 任务查询

提供只读查询接口，供 UI 系统在任务界面调用：

| 查询 | 返回 |
|------|------|
| 可见任务状态列表 | 待接取 / 进行中 / 已完成任务及其状态 |
| 各任务目标描述 | 目标类型、参数的人类可读描述 |
| 完成进度 | 每个目标的当前值 / 目标值 |

## 5. 事件契约

| 事件 | 触发时机 | 载荷关键字段 | 状态 |
|------|----------|--------------|------|
| `QuestStateChanged` | 任务状态变更 | 任务、旧状态、新状态 | ✅ 已确认 |
| `QuestProgressChanged` | 进行中任务目标进度变化 | 任务、目标索引、当前值、目标值 | ✅ 已确认 |
| `QuestAccepted` | 任务接取成功 | 任务 | ✅ 已确认 |
| `QuestCompleted` | 任务完成、奖励已发放 | 任务、奖励明细 | ✅ 已确认 |

- 事件源为场景实例 `QuestEventSource`，遵循事件-订阅规范（不引用订阅者、载荷 `readonly struct`、只广播事实）
- UI 订阅事件刷新任务界面
- 金币变更**复用**货币系统的 `CoinsChanged`，任务系统不重复广播

## 6. 架构与通信

```
QuestEventSource（场景实例，广播任务事件）
    ▲ 订阅（完成判定 / 进度推进）
    │
QuestSystem（System）──▶ 货币管理器（发放金币，Command）
    │
    ├── QuestConfig / QuestGroupConfig（ScriptableObject，静态配置）
    └── QuestInstance（运行时状态：状态 + 进度）

任务界面（UI）──查询──▶ QuestSystem（可见任务 / 描述 / 进度）
任务界面（UI）──接取──▶ QuestSystem（AcceptQuest，Command）
任务界面（UI）◀──订阅── QuestEventSource
```

| 通信 | 形式 | 方向 |
|------|------|------|
| 关键事件 → 进度推进 | 事件订阅 | QuestSystem → 事件源 |
| 奖励发放 | Command | QuestSystem → 货币管理器 |
| 任务状态广播 | 事件广播 | QuestSystem → QuestEventSource → UI |
| 可见任务 / 进度查询 | Query | UI → QuestSystem |
| 接取任务 | Command | UI → QuestSystem |

### 8.1 Q1：任务目标类型集合

**背景**

系统描述要求「系统在关键事件发生时检测所有进行中任务的目标是否达成」——这意味着**每个目标类型必须对应至少一条可订阅的事件源**，事件源是任务系统的唯一输入。目标类型的选择决定了「任务系统能表达哪些任务」：类型少了，主线配置受限制；类型多了，实现面积变大，且每个类型都有口径歧义要解决。

工程内现有事件源盘点（`Assets/Scripts/Events/`）：

| 事件源 | 可订阅事件 |
|--------|-----------|
| `ShipFlowEventSource` | ShipSpawned / ShipDestroyed / DayEnded / GameStateChanged / ExpeditionCompleted |
| `ModuleEventSource` | ModulesChanged / ModuleDestroyed / CoreExploded / RadarScanned |
| `CargoEventSource` | CargoChanged / AmmunitionConsumed / AmmunitionInsufficient / EpicCargoAcquired / CargoRevealStarted / CargoIdentified / CargoRevealCompleted |
| `WorkshopEventSource` | （待核对，工坊类事件） |

候选目标类型（与上述事件对齐）：

| 目标类型 | 参数 | 驱动事件 | 口径歧义 |
|----------|------|----------|----------|
| 摧毁敌舰 `KillEnemies` | 数量 | `ShipDestroyedEvent` | 载荷目前只有 `ship` + `reason`，**没有「击毁者」信息**。只统计玩家击毁的敌舰，还是任何飞船被毁都计？ |
| 收集货物 `CollectCargo` | 货物类别 + 数量 | `CargoChangedEvent` | 按「当前持有量」（会随消耗倒退）还是「累计获得量」（只增不减）计数？ |
| 到达目的地 `ReachDestination` | 目的地名称 | `ExpeditionCompletedEvent` | 载荷含 `destination`，直接匹配，无歧义 |
| 存活天数 `SurviveDays` | 天数 | `DayEndedEvent` | 载荷含 `dayIndex`，按「进入游戏第 N 天」计，基本无歧义 |
| （候选）获取史诗货物 | 数量 | `EpicCargoAcquiredEvent` | 已有事件，可作剧情节点 |
| （候选）装配 / 拆卸模块 | 数量 | `ModulesChangedEvent` | 可用于教学任务（如「完成首次拼装」），但载荷无具体模块信息 |

**选项**

| 方案 | 内容 | 优点 | 缺点 |
|------|------|------|------|
| A. 四类核心目标 | 摧毁敌舰 / 收集货物 / 到达目的地 / 存活天数 | 覆盖主线最常用推进点；全部由既有事件驱动 | 「摧毁敌舰」需处理击毁者判定；「收集货物」需定计数口径 |
| B. 最小子集 | 仅到达目的地 / 存活天数 | 无口径歧义，实现最简 | 主线表达力不足，难以表达战斗与收集剧情 |
| C. 四类 + 教学类 | 在 A 之上加装配 / 拆卸模块 | 可支持新手引导任务 | 需新增事件或扩展载荷，超出本版必要性 |

**推荐**

- 本版采用**方案 A（四类核心目标）**，与既有事件源一一对应，不新增伪事件；
- 「摧毁敌舰」的击毁者判定：优先在任务系统内部完成——订阅 `ShipDestroyedEvent` 时，通过 `ship` 的阵营与存活状态判断是否为本局敌方目标；若不可行，则扩展 `ShipDestroyedEvent` 载荷增加击毁者信息（涉及事件系统文档，需同步评审）；
- 「收集货物」推荐按**当前持有量**口径（与 `CargoChangedEvent.total` 载荷一致，实现成本最低）；若主线出现「交付 / 上缴货物」需求，再改累计口径；
- 教学类目标（方案 C）不在本版范围内。

**影响范围**：事件源载荷是否扩展（事件系统文档）｜任务系统事件订阅表｜任务 UI 的进度显示格式（0/N）｜完成判定逻辑

### 8.2 Q2：单目标 or 多目标

**背景**

任务节点的「目标」字段是配置表的骨架。系统描述只写了「任务目标类型、目标参数」，没有明确**一个任务是否可以挂多个目标**。多目标会引入目标间的组合逻辑（全部达成 / 任一达成），进而影响完成判定、进度显示与 UI 布局。

**选项**

| 方案 | 内容 | 优点 | 缺点 |
|------|------|------|------|
| A. 单目标字段 | `QuestConfig` 直接一个目标 | 配置最简单；完成判定 = 目标达成；进度显示单行 | 无法表达「收集货物且到达目的地」的组合任务；后续多目标需迁移配置结构 |
| B. 目标列表 + 本版仅单条 | 数据结构按 `QuestObjective[]` 预留，本版约束仅配置一条 | 结构一步到位，未来不迁移；UI 天然可扩展多行 | 本版用不到的部分带来轻微配置/实现负担 |
| C. 目标列表 + 完整组合逻辑 | 列表 + AND / OR / 阶段 | 一步到位 | 完成判定复杂化；主线用不到；实现风险大 |

**推荐**

- 采用**方案 B**：数据模型按「目标列表」设计（`QuestObjective[]`），本版约束每个任务仅配置一条、运行时只处理单目标；
- 组合逻辑（AND / OR / 分阶段）与多目标文案留待支线 / 赏金版本实现；
- 这样「配置结构」未来无需迁移，本版额外实现成本极小。

**影响范围**：`QuestConfig` 数据结构（列表 vs 单字段）｜完成判定算法（单目标判断 vs 遍历）｜UI 进度行数｜与 Q3 强相关（多目标 = 完成条件组合），建议与 Q3 一起定

### 8.3 Q3：完成条件模型

**背景**

系统描述：「完成条件由策划在配置中定义」，但没有定义完成条件的**形态**，也没有明确完成条件与「目标」的关系。这是任务系统的核心语义，直接影响状态机与判定逻辑。

**选项**

| 方案 | 内容 | 优点 | 缺点 |
|------|------|------|------|
| A. 目标达成即完成 | 单目标：完成条件 ≡ 目标达成；多目标：需组合逻辑 | 最简，符合当前单目标约束 | 无法表达阶段式任务（先收集、再交付） |
| B. 多阶段完成 | 任务拆多个阶段，阶段内单目标，依次推进 | 可表达「先收集再交付」这类剧情任务 | 运行时需 stage 状态；阶段切换判定逻辑；UI 分阶段显示 |
| C. 附加条件 | 在目标之外加时限、区域等条件 | 表达力最强 | 引入时间 / 位置维度，复杂度高 |

**推荐**

- 本版采用**方案 A 的最简形态**：单目标达成即完成，无附加条件、无阶段；
- 阶段模型（方案 B）是主线任务最可能的后续需求，在运行时状态中**预留 `stageIndex` 字段**，但本版不实现阶段切换逻辑。

**影响范围**：任务运行时状态（是否含 stage）｜完成判定触发点（单次 vs 阶段间）｜与 Q2 强相关，建议一并决策

### 8.4 Q4：任务归属方式

**背景**

系统描述：「策划可将多个任务归入同一个任务组」。「归入」在数据建模上有两种方向，决定 `QuestConfig` 与 `QuestGroupConfig` 的引用结构。若建模不当会产生双向引用环或配置遗漏。

**选项**

| 方案 | 内容 | 优点 | 缺点 |
|------|------|------|------|
| A. 任务引用组 | `QuestConfig` 上放 `QuestGroupConfig` 引用 | 配置任务时顺带指定组，直观；单向引用无环；与现有 SO 引用风格一致 | 运行时枚举「组内全部任务」需全量扫描 `QuestConfig` |
| B. 组持有任务 | `QuestGroupConfig` 上放 `QuestConfig[]` | 枚举组内任务直接；符合「组 = 清单」直觉 | 任务反查所属组不便；新增任务时易漏挂 |
| C. 双向并用 | 任务引用组 + 组持有列表（编辑器工具同步） | 双向查询都方便 | 一致性维护成本；需校验工具兜底 |

**推荐**

- 采用**方案 A（任务引用组）**，单向引用无环，与项目「显式装配」倾向一致；
- 若后续出现高频「按组分栏」需求（如任务界面按任务组分页），再叠加编辑器工具或运行时索引缓存，本版不做。

**影响范围**：`QuestConfig` / `QuestGroupConfig` 字段设计｜任务界面分栏查询逻辑｜是否引入配置校验工具

### 8.5 Q5：任务状态与进度是否存档

**背景**

货币系统已定稿「货币跨局、跨会话持久化至存档」（决策 C-1），而任务奖励金币（D-8）。因此**任务状态是否存档，直接决定金币是否会被重复刷取**、主线推进能否跨局保留：

- 若任务不存档：每次出航 / 回港循环都可能重新触发主线激活，金币可反复发放，主线推进无法跨局；
- 若任务存档：需定义存档内容（每任务状态 + 进度数值）、存档时机（状态变更时）与存档结构（复用 `GameSaveService` / `WarehouseSaveData`？）。

**前置依赖**：主线任务的存续口径——是「一局内的冒险」还是「玩家生涯推进」？当前游戏为出航-回港循环，主线大概率跨局。此口径需在主线内容确定（Q6）后确认。

**推荐**

- 本版**先不实现任务存档**，但任务状态（枚举）与进度（数值）设计为**可序列化的普通数据**，为后续接入存档预留；
- 主线内容确定后（Q6）再评估存档必要性；
- ⚠️ 若「不存档」临时成立：同一运行期内 `Completed` 状态天然防止重复发奖（状态单向流转）；跨运行期的重复问题由存档与否最终决定，需在实现时显式注意。

**影响范围**：`GameSaveService` 扩展｜任务系统运行时数据形态（可序列化性）｜金币发放的幂等性

### 8.6 Q6：主线任务内容来源

**背景**

本文档定义的是任务系统**框架**（生命周期、激活网络、事件推进、奖励对接），不包含具体主线任务内容。主线任务清单（任务名、目标、激活顺序、奖励数值）属于内容配置，需要策划输出。设定侧已有可用叙事素材（`01-设定设计`：玩家空间站背景、骚扰巨企 N、双重视角口径等），主线任务内容应对齐这些设定，但具体任务设计不在本框架文档范围内。

**待明确事项**

| 事项 | 说明 |
|------|------|
| 主线清单来源 | 由策划输出任务配置表，最终填入 `QuestConfig` 资产（SO） |
| 示例主线 | 是否需要本框架文档附带 3-5 个示例任务，覆盖线性 / 并行 / 分支三种形态，用于实现验收与联调？（推荐：需要） |

**推荐**

- 本版框架文档定稿后，策划提供至少一组**覆盖三种推进形态的示例主线**，作为实现验收基准与配置表样例。

**影响范围**：无代码影响｜影响验收标准与联调范围

### 8.7 Q7：奖励类型扩展

**背景**

系统描述：「奖励规则定义任务完成时发放的奖励类型和数量」。本版明确只做金币，但结构上需要决定**是否按列表预留多类型**——这决定未来加货物 / 模块奖励时是「扩展字段」还是「迁移配置」。

候选奖励类型与发放路径：

| 奖励类型 | 发放路径 | 复杂度 |
|----------|----------|--------|
| 金币 | 货币管理器（已有 `CoinsChanged`） | 低 |
| 货物 | 货舱 / 仓库（需空间判定，可能放不下） | 中 |
| 模块 | 仓库（自由格，可能已满） | 中 |
| 解锁内容 | 商店商品解锁 / 地图区域解锁 | 高 |

**推荐**

- `QuestConfig` 奖励字段按**列表**设计（`QuestReward[]`：奖励类型枚举 + 数量 + 可选目标引用），本版填充**单条金币奖励**；
- 发放逻辑先只实现金币分支；货物 / 模块奖励的发放路径需与货币 / 仓库系统文档同步后补充设计；
- 与 Q2 的目标列表预留思路一致：**列表存储，本版单条使用**，避免未来配置迁移。

**影响范围**：`QuestConfig` 数据结构｜奖励发放服务（本版仅金币分支）｜货币 / 仓库系统的对接边界
