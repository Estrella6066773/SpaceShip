# 模块分层与粘合代码模式

> 作者：代码分析生成 | 创建日期：2026-08-02 | 最后修改：2026-08-02

本文档定义 Spaceship 项目新一轮重构的目标组织模式：**摈弃按程序员划分功能，完全面向模块区分**，采用「多层独立模块 + 粘合代码嵌套」的组合方式。

## 背景与目标

### 现状问题

工程代码目前按开发者目录划分（`Assets/Kaki`、`Assets/wuqiwusheng`、`Assets/Mailk`），存在三类结构性问题：

1. **同一职责出现多份实现**：敌舰行为存在两个并行宿主；视野半径存在两套算法；「世界目标点 → 移动输入」的导航转换在敌舰侧复制了两份。
2. **输入设备代码内嵌在能力模块内部**：`ShipMotionController` 内嵌 WASD 读取，`ShipCombatController` 内嵌鼠标左键读取，交互、降落、货物界面各自直接读取输入设备。
3. **模块边界与开发者归属混淆**：本应属于同一个模块的概念（如敌舰行为 = 决策 + 适配 + 驱动），被人为拆到两个开发者目录。

### 目标模式

**多层独立模块 + 粘合代码嵌套**：

- 系统由若干**能力模块**按层组织，每个模块只封装一个独立的领域能力，不感知使用方是谁。
- 模块之间的组合由**粘合代码**完成：粘合代码以嵌套方式逐层装配，把上层模块的输出接到下层模块的输入。
- 玩家、敌人、工坊等不同使用方，共用同一套能力模块与粘合方式，仅在「输入源」这一层产生差异。

## 模式定义

### 两类构成物

| 构成物 | 职责 | 允许拥有 | 禁止拥有 |
|--------|------|----------|----------|
| **能力模块** | 封装一个领域能力 | 该领域的规则、状态、对外接口 | 输入设备代码、对使用方的反向引用、流程协调 |
| **粘合代码** | 把模块接线组合 | 引用模块、输入源、事件源，做「接线」 | 领域规则、数值计算、业务决策 |

### 三类粘合代码

| 类型 | 作用 | 示例 |
|------|------|------|
| **输入粘合** | 把输入源接到能力模块 | 玩家输入系统 → 移动模块；敌人 AI 决策 → 移动模块 |
| **装配粘合** | 在场景/初始化时组合模块实例 | Inspector 拖引用、初始化器注入模块引用 |
| **适配粘合** | 适配跨模块的接口差异 | `EnemyShipController` 实现 `IEnemyShipRuntime` 把 AI 决策转成飞船指令 |

### 粘合代码规则

1. 粘合层**不得包含领域规则**，只做接线与转换。
2. 粘合层**不得做数值计算**（移动性能、伤害、消耗等算法必须留在能力模块内）。
3. 能力模块**不得反向引用粘合层**，只能通过接口被驱动。
4. 若两块粘合代码出现大量重复，说明背后应该存在一个独立能力模块，重复的接线应上提为模块接口。

## 模块分层

能力模块按「离输入设备/具体实体多远」分为四层：

```
L3 流程层   Director / 游戏流程          ← 协调跨系统流程
L2 决策层   玩家输入系统 / 敌人 AI 决策    ← 产生「行动指令」
L1 指令层   导航转换 / 交互指令转换        ← 把意图转成模块可执行的指令
L0 执行层   移动物理 / 武器 / 货舱 / 组装   ← 执行一个具体领域的规则
```

| 层 | 角色 | 代表 | 知道谁在用自己吗 |
|----|------|------|------------------|
| L0 执行层 | 领域能力执行 | `ShipMotionController`、`ShipAssembly`、`ShipCargoHold`、`ShipCombatController` | 不知道 |
| L1 指令层 | 意图 → 可执行指令 | `ShipNavigation`（目标点 → 局部移动输入） | 知道要提供「移动到目标」语义，不知道调用方是玩家还是 AI |
| L2 决策层 | 依据感知与规则产生意图 | 玩家输入系统、敌人行为状态机 | 知道 L0/L1 提供的接口 |
| L3 流程层 | 跨模块协调 | `TemporaryGameDirector`、`SpaceshipGameFlowController` | 知道所有子系统 |

### 与现有四层模型的关系

本模式**不推翻**现有的 Director / System / Actor / EventSource 四层架构，而是补充「输入源」这一新概念，并重新定义层间接线的形式：

| 现有模型 | 对应本模式 |
|----------|-----------|
| System | L0 执行层（领域规则） |
| Actor | L0 执行层上的具体实体实例 |
| Director | L3 流程层 |
| EventSource | 各模块共同的「事实广播」通道，不属于任何一层 |
| **（新增）输入源** | **L2 决策层**：玩家输入系统、敌人 AI 输入系统 |

## 输入系统统一

### 统一行动指令

所有输入源（玩家、敌人 AI、工坊试驾、验收脚本）产生同一种**帧级行动指令**：

```csharp
/// <summary>
/// 一份帧级行动指令，由输入源产生，交给飞船能力模块消费。
/// Move 为局部空间（y 轴前后推进），Turn 为转向输入（-1..1），Fire 为开火意图。
/// </summary>
public readonly struct ShipActionCommand
{
    public ShipActionCommand(Vector2 move, float turn, bool fire)
    {
        Move = move;
        Turn = turn;
        Fire = fire;
    }

    public Vector2 Move { get; }
    public float Turn { get; }
    public bool Fire { get; }

    public static readonly ShipActionCommand None = new(Vector2.zero, 0f, false);
}
```

### 统一输入源接口

```csharp
/// <summary>
/// 统一的行动指令输入源。玩家输入系统、敌人 AI 输入系统、
/// 工坊试驾和验收脚本各自实现；飞船的移动/战斗模块只消费指令，不感知来源。
/// </summary>
public interface IShipActionInput
{
    /// <summary>当前是否允许产生行动指令。</summary>
    bool ActionsEnabled { get; }

    /// <summary>开启或关闭行动能力；关闭时必须立即返回 None 指令。</summary>
    void SetActionsEnabled(bool enabled);

    /// <summary>读取本帧行动指令。</summary>
    ShipActionCommand ReadCommand();
}
```

### 输入源清单

| 输入源 | 实现 | 产生指令 |
|--------|------|----------|
| 玩家输入系统 | 读取 Input System（WASD + 鼠标） | 移动 / 转向 / 开火 |
| 敌人 AI 输入系统 | 敌人行为状态机 → `ShipNavigation` | 移动 / 转向 / 开火 |
| 工坊试驾输入 | 工坊面板 | 移动 / 转向 / 开火 |
| 验收脚本输入 | 验收脚本直接构造指令 | 任意 |

### 装配方式

飞船实体在装配时选择自己的输入源并注入到能力模块：

```
玩家飞船  ──► PlayerShipInputSystem ──► ShipMotionController / ShipCombatController
敌舰      ──► EnemyBehaviorStateMachine ──► EnemyAiInputSystem ──► 同上
工坊试驾  ──► WorkshopDriveInputSystem ──► 同上
```
