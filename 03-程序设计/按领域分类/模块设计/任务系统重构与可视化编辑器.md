# 任务系统重构与可视化编辑器设计

> 类型：程序设计（修订） | 依据：《任务系统（系统设计）》《任务系统（程序设计）》
> 状态：设计草案，待确认 | 更新：2026-08-13
>
> 本文档是对《[任务系统](./任务系统.md)》（程序设计）的**一次重构修订**，并新增配套的**可视化任务流程编辑器**设计。业务决策沿用原文档，本文档只描述变化部分。
>
> 变更点：
> 1. **英文代号 Quest → Mission**（中文「任务」保持不变）。
> 2. **配置架构改造**：任务由 `ScriptableObject` 直接配置，改为「纯数据类 `Mission` + 集中式 `MissionDatabase`（SO 容器）」，并支持 JSON 导入/导出。
> 3. **任务达成模型重构**：以「结局进度条」为唯一达成单元，替代原「顺序阶段 + 四类目标」模型；顺序引导交由任务链（节点图）表达。
> 4. **职责分层**：拆成「任务链模块（纯拓扑 + 状态机）」与「目标追踪子模块（具体领域判定，可插拔）」，判定外置、进度状态集中。
> 5. **全局进度计数器**：承载「独一」进度——任务未开放也累计、可跨任务跨会话持久。
> 6. **新增可视化编辑器工具**：策划以节点图方式编排任务网络。

## 1. 变更背景

现有任务系统已按 `QuestConfig : ScriptableObject` 实现并落盘为 7 个分散资产（6 个任务 + 1 个任务组）。本次重构要解决的问题：

| 问题 | 现状 | 目标 |
|------|------|------|
| 前置关系不可见 | 任务间依赖藏在资产引用里，策划看不到拓扑全貌 | 画布上直接看到任务网络与结局分支 |
| 任务不是独立类 | 配置依附于 ScriptableObject | 任务抽象为纯数据类 `Mission` |
| 达成模型僵化 | 「顺序阶段 + 四类目标」写死，表达不了并行选择 | 「结局进度条」统一量化与一次性达成，顺序交给任务链 |
| 无预累计 | 接取任务后才开始累计进度 | 「独一」进度可跨任务、跨会话预累计 |
| 无结果分支 | 只能线性 + All/Any 前置 | 任务多结局，不同结局导向不同后续 |

### 1.1 架构定位

本文档描述的是一套**以「事件驱动」为通信骨架、以「领域模块化 + 贫血数据模型」为组织方式、以「可插拔策略」实现扩展、以「端口-适配器」隔离核心域的复合架构**，核心原则是「判定外置、状态集中」。

**主归类：事件驱动架构（EDA）**

通信骨架是事件-订阅，这是最底层的约束（对齐项目《事件-订阅》规范）：

- 事件源（`MissionEventSource` / `ShipFlowEventSource` 等）**只广播事实，不感知订阅者、不执行业务规则**；
- 事件载荷一律 `readonly struct`，避免堆分配；
- 任务链模块、奖励模块、追踪器之间全部经事件解耦，不互相持有引用。

**三个支撑特征**

1. **领域模块化 + 贫血数据模型（借 DDD 思路，非经典 DDD）**：按领域职责拆模块，但 `Mission` / `MissionEnding` 是纯 `[Serializable]` 数据类（无行为），行为集中在领域服务 `MissionService`。是「贫血模型 + 领域服务」，而非充血实体。
2. **可插拔策略（Strategy）**：目标类型由「枚举 + 参数字段 + 追踪器实现 + 工厂 `Create()`」构成。新增目标类型只加枚举 + 追踪器 + 工厂分支，任务链框架不动；`IMissionObjectiveTracker` 即策略接口，工厂按类型选择策略。
3. **端口-适配器（六边形）雏形**：核心域 `MissionService` 只依赖窄接口（`IMissionObjectiveTrackerFactory`）、纯数据（`MissionDatabase`）与事件广播，**不持有事件源、不持有 `CoinManager`、不感知追踪器构造细节**。工厂、事件桥、回调上报本质上是「端口」，把核心域与外部世界（事件源、经济系统、UI）隔离。

**标志性原则：判定外置、状态集中**

- 进度「怎么判定」外置到追踪子模块（策略）；
- 进度「当前数值」集中在任务链模块（非 `unique`）或全局计数器（`unique`）；
- 追踪器只上报规范化结构 `MissionObjectiveReport`，不持有状态。

**非以下架构**（避免表面相似误判）：非 ECS（无实体+组件+系统的扁平数据驱动）、非严格 DDD（贫血模型、无聚合根/值对象）、非严格六边形（端口未显式抽象为接口层，事件源注入是「装配期例外」）、非 MVC（无 Controller 层，UI 走事件订阅）。本质是从项目自身《事件-订阅》规范与「通信模式分离」（Query / Command / Callback / Event / 依赖注入）这棵根上长出的**领域模块化架构**。

## 3. 数据模型：结局进度条 + 全局进度计数器

### 3.1 设计原则

- **`Mission` 等数据类是纯 `[Serializable]` C# 类**，不继承任何 Unity 类型；它们就是「任务」领域对象的直接表达。
- 数据类字段用 `public` 字段：便于 `JsonUtility` 直接序列化、便于编辑器工具直接读写。
- **任务间引用改用字符串 ID**：前置任务、后续任务、所属组均用 ID 表达，由 `MissionDatabase` 统一解析。
- **任务 = 一组并行结局**：没有顺序阶段；每个结局是一条进度条，达成即进入该结局。顺序引导由任务链（结局 → 后续任务）表达。
- **结局进度条统一量化与一次性达成**：进度通过「追踪器监听事件 + 系统提交」累计，达到 n 格上限即进入该结局。
- **判定外置、状态集中**：进度「怎么判定」外置到目标追踪子模块（§5.5），「当前数值」由任务链模块或全局计数器持有。
- **接取事件化**：接取不是 UI 专属命令，而是「接取任务」事件消息；任务中心只是接取点之一，任意系统 / 场景 / 触发器均可广播接取事件。任务可设 `autoStart` 在开放后自动开始（跳过接取事件）。
- **隐藏与全局累计正交**：`hidden`（是否对玩家可见）与 `unique`（进度是否全局持久）是两个独立维度，可自由组合（§3.8）。
- **集中式数据库**：一个 `MissionDatabase` 资产持有全部任务与任务组。

### 3.2 数据类定义

```csharp
// 文件：Scripts/Data/Mission/Mission.cs
// 命名空间：Spaceship.Data.Mission

/// <summary>任务：由「展示 + 触发 + 结局 + 事件」构成的领域对象。</summary>
[Serializable]
public sealed class Mission
{
    public string missionId;                              // 跨会话稳定 ID

    // ── 展示 ──
    public string title;                                  // 标题
    public string brief;                                  // 简介（一句话）
    public string detail;                                 // 详情（多段描述）

    // ── 归属 ──
    public string groupId;                                // 所属任务组 ID

    // ── 可见性与接取 ──
    public bool hidden;                                   // 隐藏：不显示给玩家（编辑器/调试可见）
    public bool autoStart;                                // 开放后自动开始（跳过接取事件）

    // ── 触发 ──
    public List<MissionPrerequisite> prerequisites = new();  // 前置任务（含「来自哪个结局」）
    public List<MissionListenableEvent> triggerEvents = new();  // 监听的外部事件（触发用，白名单枚举）
    public MissionTriggerLogic triggerLogic = MissionTriggerLogic.All;  // All / Any

    // ── 开端 ──
    public string startEventName;                         // 任务开始时广播的事件

    // ── 结局（互斥达成：多结局只能通过其一；顺序 = 优先级） ──
    public List<MissionEnding> endings = new();           // 空 = 无有效达成（校验错误）
}

/// <summary>前置任务条目：任务 ID + 该任务的某个结局标识。</summary>
[Serializable]
public sealed class MissionPrerequisite
{
    public string missionId;        // 前置任务 ID
    public string endingId;         // 前置任务的结局标识（空 = 任意结局完成）
}

/// <summary>任务组：组 ID + 显示名；组内任务由任务的 groupId 反向归属。</summary>
[Serializable]
public sealed class MissionGroup
{
    public string groupId;
    public string displayName;
}

/// <summary>
/// 结局：任务的一个达成分支。进度条达到 n 格即进入该结局。
/// 多个结局同时达成时，列表顺序靠前者（优先级高）生效。
/// 失败也是一种结局（endingKind = Failure），任务不设独立失败状态。
/// </summary>
[Serializable]
public sealed class MissionEnding
{
    public string endingId;                              // 结局标识（任务内唯一）
    public string endingTitle;                           // 结局标题（可选，展示/调试用）
    public MissionEndingKind endingKind = MissionEndingKind.Success;  // 成败性质（UI 渲染/校验/事件用）

    // ── 进度条 ──
    public MissionObjectiveType objectiveType;           // 进度来源类型（对应追踪器）
    public int targetValue = 1;                          // n 格上限
    public CargoType cargoType;                          // CollectCargo 参数（与 CargoChangedEvent 载荷对齐）
    public string destinationName;                       // ReachDestination 参数
    public MissionListenableEvent listenEvent;           // ListenEvent 参数：监听的可监听事件（白名单枚举）

    // ── 独一（全局累计） ──
    public bool unique;                                  // 是否使用全局进度计数器
    public string globalProgressId;                      // unique 时的计数器 key

    // ── 奖励 + 后续 ──
    public List<MissionReward> rewards = new();          // 该结局的奖励
    public List<string> followupMissionIds = new();      // 该结局触发的后续任务（与前置双向同步）
}

/// <summary>奖励条目。</summary>
[Serializable]
public sealed class MissionReward
{
    public MissionRewardType rewardType = MissionRewardType.Gold;
    public int amount;
}
```

### 3.4 目标类型可扩展机制（目标追踪子模块）

「底层框架固定、目标类型可插拔」的落地：目标类型由「枚举 + 数据参数 + 目标追踪器」构成。**判定逻辑外置到目标追踪子模块，进度状态集中**。

新增一种目标类型时（程序扩展，策划通过配置选用）：

1. `MissionObjectiveType` 加枚举值；
2. `MissionEnding` 若需新参数，加字段；
3. 新增一个目标追踪器 `XxxTracker`（实现追踪器协议，见 §5.5），负责监听领域事件并上报增量/达成；
4. `GetObjectiveDescription` 加描述模板。

四类目标与 `ListenEvent` 均为该机制下的预设模板，各自对应一个追踪器。

**`ListenEvent` 的可监听事件来源**：`ListenEvent` 的 `listenEvent` 字段不是自由字符串，而是 `MissionListenableEvent` 枚举（§3.3）。该枚举即「可监听事件白名单」，由 `MissionListenableEventBridge`（§5.5）映射到具体强类型领域事件订阅。任务「触发事件 `triggerEvents`」与结局「监听事件 `listenEvent`」**共用同一张白名单与同一座桥**，避免两套命名。

> 与 D-9 的关系：四类目标（D-9）保持不变，只是从「写死的枚举 + 顺序阶段」升级为「可扩展类型系统的初始成员」，直接挂载在结局进度条上。`ListenEvent` 为新增基础类型。
>
> 事件载荷为强类型 `readonly struct`，无法纯数据驱动，故新增目标类型或新增可监听事件仍需写代码（追踪器/桥接线 + 枚举 + 描述模板），但任务链框架无需改动。

### 3.5 MissionDatabase（SO 容器）

```csharp
// 文件：Scripts/Data/Mission/MissionDatabase.cs
// 命名空间：Spaceship.Data.Mission

/// <summary>任务数据库：集中持有全部任务与任务组，提供 ID 查询、校验与 JSON 导入导出。</summary>
[CreateAssetMenu(menuName = "Spaceship/任务/任务数据库", fileName = "任务数据库")]
public sealed class MissionDatabase : ScriptableObject
{
    [SerializeField] private List<Mission> missions = new();
    [SerializeField] private List<MissionGroup> groups = new();

    public IReadOnlyList<Mission> Missions => missions;
    public IReadOnlyList<MissionGroup> Groups => groups;

    public Mission GetMission(string missionId);
    public MissionGroup GetGroup(string groupId);
    public bool Validate(out List<string> errors);
}
```

**校验规则**（对齐原 `QuestConfig.IsValid`，并新增）：
- `missionId` 唯一且非空；
- `endings` 非空（任务至少一个结局）；
- `prerequisites` 不包含自身，每个 `missionId` 都能查到，`endingId` 若非空须在该前置任务的 `endings` 中；
- `triggerEvents` 非空合法（现为 `MissionListenableEvent` 枚举，校验改为「成员有效」，无字符串校验）；
- `groupId` 为空或能查到；
- `endings[].endingId` 唯一；
- `endings[].followupMissionIds` 每个都能查到；
- `endings[].objectiveType == ListenEvent` 时 `listenEvent` 需为有效枚举成员（桥覆盖范围内）；
- `endings[].unique == true` 时 `globalProgressId` 非空；
- `endings[].endingKind == Failure` 时 `rewards` 建议为空（警告级，非阻断——失败结局通常不发正奖励，惩罚由后续任务表达）；
- `hidden == true` 时建议 `autoStart == true`（警告级，非阻断——隐藏任务通常自动开始，否则无人可接取）；
- **无循环依赖**（沿「前置 → 后续」双向对有向图做环检测）。

### 3.6 结局与结果语义

任务 A 的结局 `endingId = X` 指向任务 B，等价于 B 的 `prerequisites` 含「A + X」。`MissionDatabase` 是解析 ID 的唯一入口。

**结局互斥达成**：一个任务可配置多个可选结局，但**只能达成其中一个**——某个结局先达标即生效，任务进入 `Completed`，其余结局作废。常见形态是**单结局任务**（`endings` 只配一个，主线大多如此）；多结局用于「单任务多出口」的分支/成败场景。

**失败是一种结局，不是状态**：任务失败不引入独立状态（`MissionState` 保持 `Inactive / Available / InProgress / Completed` 四态）。失败用**失败结局**表达——一个普通的 `MissionEnding`，典型配置：

- 「存活 N 天」任务的失败结局 = `objectiveType = ListenEvent` + `listenEvent = 玩家飞船被摧毁`（或对应失败事件）；
- 失败结局达成 → 任务同样进入 `Completed`（「已终结」），广播 `MissionEndedEvent`（`endingId` = 失败结局标识）；
- 失败结局的 `followupMissionIds` 指向惩罚/补偿/后续分支任务，与成功结局的后续机制完全一致。

**成败如何区分**：由「最终达成的结局」区分，而非状态。`MissionEndedEvent` 携带 `endingId`，订阅者据此判定成功/失败；存档记录 `completedEndingId`（§6.1）以持久化「达成了哪个结局」，供后续任务的前置判定与 UI 展示。

**结局判定逻辑**（运行时）：

1. 任务进行中，所有结局的进度条**并行**累计（各自监听事件，各自推进）。
2. 某个结局进度达到 `targetValue` → 进入该结局：
   - 广播 `MissionEndedEvent`（载荷携带 `endingId` + `endingKind`；奖励尚未发放，由 §5.7 奖励模块订阅后派发）；
   - 状态置 `Completed`；
   - 停止其余结局的追踪器（其余结局作废，不再推进）；
   - 激活 `followupMissionIds` 对应的后续任务（触发新一轮激活检测）。
3. **多结局同时达标**：按 `endings` 列表顺序，靠前者（优先级高）生效，其余作废。
4. **`unique` 结局**：进度来源是全局计数器（§3.7），任务未开放时计数器已在累计；任务开放后读取计数器判断是否达成（详见 §5.6）。

### 3.7 全局进度计数器（独一进度的载体）

`unique == true` 的结局，其进度不存任务级，而存**全局进度计数器**——独立于任务生命周期的持久累计器。

| 特性 | 说明 |
|------|------|
| 存储 | `SaveData.globalProgress`（`List<GlobalProgressEntry>`：`progressId` + `value`） |
| 生命周期 | 跨任务、跨会话持久，单调递增，任务完成也不归零 |
| 预累计 | 全局追踪器常驻监听事件，任务未开放也在累计 |
| 一次性 | 计数器满后不重置，配合任务状态（`Completed` 不重新激活）实现「一存档只完成一次」 |

```csharp
// 文件：Scripts/Data/Mission/GlobalProgress.cs
// 命名空间：Spaceship.Data.Mission

/// <summary>全局进度计数器条目：progressId 为跨会话稳定 key。</summary>
[Serializable]
public sealed class GlobalProgressEntry
{
    public string progressId;
    public int value;
}
```

**全局追踪器**（常驻，对应 `unique` 目标的累计）与**任务级追踪器**（临时，对应非 `unique` 目标）共用同一套追踪器协议（§5.5），区别仅在于：
- 全局追踪器由常驻宿主 `MissionGlobalProgressHost`（跨场景单例，§5.8）创建并持有，写入全局计数器；
- 任务级追踪器由 `MissionService` 在接取/进入结局判定时创建，上报任务级进度，任务收尾时销毁。

### 3.8 接取语义与任务可见性

#### 3.8.1 接取事件化

接取不再绑定「任务中心 UI 按钮」这一处动作，而是抽象为**事件消息**。任务系统监听「接取任务」事件，任意系统 / 场景 / 触发器均可广播该事件请求接取：

- 任务中心（休整站 `MissionPanel`）是**主要接取点**，点击「接取」= 广播一次接取事件；
- 其他系统（剧情触发器、NPC 交互、关卡脚本等）同样可广播接取事件；
- 任务系统收到事件后判定：任务处于 `Available` 才接取成功，否则忽略（或广播拒绝事实）。

#### 3.8.2 autoStart 与状态机

`autoStart == true` 的任务在**激活后直接进入 `InProgress`**，不经过 `Available`、不等待接取事件。`autoStart == false` 的任务激活后停在 `Available`，等待接取事件。

状态流转（双向路径）：

```
Inactive ──触发条件满足──▶ Available ──接取事件──▶ InProgress ──结局达成──▶ Completed
                                      ▲
Inactive ──触发条件满足──▶ InProgress（autoStart == true）
```

#### 3.8.3 hidden 与可见性

`hidden == true` 的任务不显示给玩家：

| 视角 | 是否可见 |
|------|----------|
| 玩家（`MissionPanel` / 探索 HUD） | 不可见 |
| 策划（编辑器画布） | 可见（画布上标记「隐藏」样式） |
| 开发者（调试 / 日志 / 存档） | 可见 |

`GetVisibleQuests()` 排除 `hidden` 任务；`GetAllQuests()` 返回全部（含隐藏，供调试）。隐藏任务常用于底层规则计数（如「事件 E 发生 50 次后开启任务 B」，见 §3.8.4）。

#### 3.8.4 隐藏任务作为规则引擎

任务系统可承担**底层规则/条件**，典型模式：

```text
隐藏任务 A（hidden = true, autoStart = true）
  ├── 结局：objectiveType = ListenEvent, listenEvent = EnemyShipDestroyed, targetValue = 50
  ├── unique = true, globalProgressId = "Rule_EnemyDestroyed_50"
  └── followupMissionIds = [B]

任务 B（正常显示）
  └── prerequisites = [A 的该结局]
```

「敌舰被摧毁 50 次后开启 B」由隐藏任务 A 的全局计数器累计，达成后 A 完成并扇出激活 B，玩家全程无感知。**四个正交维度**（`hidden` / `autoStart` / `unique` / `triggerEvents`）可自由组合出「成就」「隐藏规则」「后台计数」「一次性解锁」等多种任务形态，无需新增底层机制。

## 5. 运行时改造

### 5.1 MissionRuntimeState

```csharp
public sealed class MissionRuntimeState
{
    public Mission Mission { get; }
    public MissionState State { get; internal set; }
    // 每个非 unique 结局的任务级进度（unique 结局读全局计数器，不入此处）
    // 单结局任务仅一个键；多结局互斥并行时各结局各自累计，达成一个即收尾
    public IReadOnlyDictionary<string, int> EndingProgress { get; }
}
```

任务级进度按 `endingId` 存字典：非 `unique` 结局各有独立进度值；`unique` 结局不在此字典，运行时直接读全局计数器。**单结局是常见形态**（字典仅一个键）；多结局互斥并行时多个键并存，某键达标即进入该结局并收尾。

### 5.2 MissionService

构造签名变更：

```csharp
// 旧：public MissionService(IReadOnlyList<QuestConfig> allQuestConfigs, SaveData saveData, CoinManager coins)
// 新：
public MissionService(MissionDatabase database, SaveData saveData, IMissionObjectiveTrackerFactory trackerFactory)
```

> 注意：
> - `CoinManager` 依赖被**移除**——奖励发放外置到独立的奖励派发模块（§5.7）；
> - 新增 `IMissionObjectiveTrackerFactory`（§5.5.2）——任务链模块**不直接构造追踪器、不持有事件源引用**，需创建追踪器时向工厂索取。

内部改造（业务逻辑核心不变）：
- `statesById` 键用 `mission.MissionId`（与旧 `QuestId` 等价）；
- **触发判定** `IsTriggerSatisfied`：遍历 `prerequisites`（含 `endingId`）经 `database` 解析查状态 + `triggerEvents` 是否触发（经桥订阅，§5.5.1）+ `triggerLogic` 组合；
- **激活**：触发满足 → `autoStart ? InProgress : Available`（`autoStart` 跳过接取等待）；
- **接取** `AcceptMission`：监听接取事件，仅 `Available` 可接取 → `InProgress`；`autoStart` 任务不响应接取事件；
- **结局进度推进**：非 `unique` 结局经 `trackerFactory.Create(ending.objectiveType)` 创建任务级追踪器（§5.5.2）上报进度；`unique` 结局读全局计数器；
- **结局判定** `ResolveEnding`：任一结局进度达标 → 收尾（广播 `MissionEndedEvent`、激活后续、停其余追踪器）；多结局同时达标按列表顺序取前；
- **不发奖励**：结局达成只广播事实，奖励由 `MissionRewardDispatcher` 订阅后派发（§5.7）；
- 其余（持久化）逻辑保持一致。

### 5.3 MissionSystem（场景装配器）

```csharp
[SerializeField] private MissionDatabase database;   // 原 List<QuestConfig> questConfigs 改为单个数据库引用
```

`EnsureInitialized()` 内装配顺序：
- 创建 `MissionListenableEventBridge` 并 `Wire(...)` 注入事件源（§5.5.1）；
- 创建 `MissionObjectiveTrackerFactory(flow, cargo, bridge)` 追踪器工厂（§5.5.2，构造注入事件源）；
- `new MissionService(database, data, trackerFactory)` 创建任务链模块；
- 调用 `MissionGlobalProgressHost.Instance?.Rebind(flow, cargo, data)` 重绑定常驻宿主（§5.8）；
- 装配奖励派发模块 `MissionRewardDispatcher`（§5.7，注入 `CoinManager` 与 `MissionEventSource`）。

休整站与探索场景各自引用同一 `MissionDatabase` 资产；全局进度宿主（常驻）不在此创建，由 §5.8.1 模式在首个场景自建并跨场景保留。

### 5.4 事件源

`MissionEventSource` 及 `readonly struct` 载荷，类型名从 `QuestXxx` 改为 `MissionXxx`，载荷字段 `Mission Mission` 类型由 `QuestConfig` 改为 `Mission`。事件名与 `RaiseXxx` 方法同步改名；`QuestCompletedEvent` → `MissionEndedEvent`（载荷含 `Mission` + `endingId` + `endingKind`）。移除 `QuestStageChangedEvent`。

新增/调整事件：

| 事件 | 方向 | 载荷 | 说明 |
|------|------|------|------|
| `MissionAcceptRequested` | 广播（外部 → 任务系统） | `missionId` | **接取事件化**：任意系统广播请求接取；任务系统监听后判定 |
| `MissionAccepted` | 广播（任务系统 → 外部） | `Mission` | 接取成功事实 |
| `MissionStateChanged` | 广播（任务系统 → 外部） | `Mission` + 旧/新状态 | 含激活、接取、完成 |
| `MissionProgressChanged` | 广播（任务系统 → 外部） | `Mission` + `endingId` + 当前值/目标值 | 结局进度变化 |
| `MissionEnded` | 广播（任务系统 → 外部） | `Mission` + `endingId` + `endingKind` | 结局达成；`endingKind` 供订阅者区分成败（奖励尚未发放） |
| `MissionRewardGranted` | 广播（奖励模块 → 外部） | `Mission` + `endingId` + 发放明细 | 奖励已实际发放（供 UI 展示到账，由 §5.7 奖励模块广播） |

> 接取请求方向辨析：`MissionAcceptRequested` 是外部系统广播的「有人想接取任务」事实，遵循事件-订阅规范（任务系统只监听，不感知广播者）。接取「是否成功」由任务系统判定后通过 `MissionAccepted`（成功事实）体现；失败场景不广播成功事件（UI 可自行判断任务状态是否变为 `InProgress`）。

### 5.5 目标追踪子模块（判定外置、可插拔）

目标追踪子模块承担「具体目标怎么判定达成」的领域逻辑。核心约束：

- **判定外置**：追踪器负责「事件筛选 + 进度规则 + 是否达成」，任务链模块不理解任何目标类型语义。
- **状态集中**：追踪器**不持有进度状态**，只上报「进度更新」；进度数值由任务链模块（非 `unique`）或全局计数器（`unique`）统一持有。
- **统一上报收口**：追踪器不各自命名事件，统一通过回调上报规范化结构。

```csharp
// 文件：Scripts/Gameplay/Mission/ObjectiveTracking/IMissionObjectiveTracker.cs
// 命名空间：Spaceship.Gameplay

/// <summary>目标追踪器协议：每个目标类型一个实现，负责判定并上报进度，不持有进度状态。</summary>
public interface IMissionObjectiveTracker
{
    MissionObjectiveType Type { get; }

    void Start(MissionEnding ending, Action<MissionObjectiveReport> report);
    void Stop();
}

/// <summary>追踪器向外部上报的规范化更新（只上报，不累计）。</summary>
public readonly struct MissionObjectiveReport
{
    public readonly int Increment;    // 增量（累加型目标）
    public readonly int Absolute;     // 绝对值（取总量型目标，如 CollectCargo）
    public readonly bool Completed;   // 一次性达成（如 ReachDestination / ListenEvent）
}
```

预设追踪器（与目标类型一一对应）：

| 追踪器 | 订阅的领域事件 | 上报规则 |
|---|---|---|
| `KillEnemiesTracker` | `ShipDestroyedEvent` | 敌舰（`Ship.Faction == Enemy`）→ `Increment = 1` |
| `CollectCargoTracker` | `CargoChangedEvent` | 类别匹配（`CargoType`）→ `Absolute = total` |
| `ReachDestinationTracker` | `ExpeditionCompletedEvent` | 目的地匹配（`Destination`）→ `Completed = true` |
| `SurviveDaysTracker` | `DayEndedEvent` | `Increment = 1` |
| `ListenEventTracker` | 经桥订阅（见下） | `listenEvent` 对应事件触发 → `Completed = true` |

#### 5.5.1 可监听事件桥（ListenEvent 与 triggerEvents 的订阅通道）

`ListenEvent` 与任务的 `triggerEvents` 都无法直接按「字符串事件名」订阅强类型 `readonly struct` 事件，故引入 `MissionListenableEventBridge` 作为**唯一通道**：

```csharp
// 文件：Scripts/Gameplay/Mission/ObjectiveTracking/MissionListenableEventBridge.cs
// 命名空间：Spaceship.Gameplay

/// <summary>
/// 可监听事件桥：把 MissionListenableEvent 白名单映射到具体强类型领域事件订阅。
/// 不保存进度、不执行业务规则，只做「枚举 → 订阅/反订阅」的归一化接线。
/// </summary>
public sealed class MissionListenableEventBridge
{
    // 装配期注入事件源（依赖注入例外：场景装配期显式引用）
    public void Wire(ShipFlowEventSource shipFlow, CargoEventSource cargo, /* ... */);

    public void Subscribe(MissionListenableEvent evt, Action handler);
    public void Unsubscribe(MissionListenableEvent evt, Action handler);
}
```

- **装配**：`MissionSystem` 初始化时调用 `Wire(...)` 注入事件源，桥内部按枚举接线（如 `EnemyShipDestroyed → shipFlow.ShipDestroyed`，其中桥自己过滤 `Ship.Faction == Enemy`）。
- **消费**：`ListenEventTracker` 与触发判定都通过桥 `Subscribe(listenableEvent, handler)` / `Unsubscribe(...)`，**不直接持有事件源引用**。
- **触发事件复用**：任务开放判定 `IsTriggerSatisfied` 里的 `triggerEvents` 也通过桥订阅（`triggerLogic` 组合 All/Any），与结局监听共用同一张白名单、同一座桥。
- **扩展**：新增可监听事件 = `MissionListenableEvent` 加枚举 + 桥内加一条接线 + （若需筛选）在桥内加过滤。

#### 5.5.2 追踪器工厂（事件源注入点）

四个玩法追踪器（`KillEnemiesTracker` 等）直接订阅强类型领域事件，它们的**事件源引用在构造时注入**——由追踪器工厂在场景装配期创建并持有事件源，任务链模块不直接接触事件源：

```csharp
// 文件：Scripts/Gameplay/Mission/ObjectiveTracking/IMissionObjectiveTrackerFactory.cs
// 命名空间：Spaceship.Gameplay

/// <summary>追踪器工厂协议：按目标类型创建追踪器实例。</summary>
public interface IMissionObjectiveTrackerFactory
{
    /// <summary>为指定目标类型创建追踪器；返回 null 表示该类型无对应追踪器。</summary>
    IMissionObjectiveTracker Create(MissionObjectiveType type);
}

// 文件：Scripts/Gameplay/Mission/ObjectiveTracking/MissionObjectiveTrackerFactory.cs
/// <summary>
/// 追踪器工厂：场景装配期创建，构造时注入各事件源与桥，
/// 按目标类型返回对应追踪器实例（追踪器构造时接收事件源）。
/// </summary>
public sealed class MissionObjectiveTrackerFactory : IMissionObjectiveTrackerFactory
{
    private readonly ShipFlowEventSource shipFlow;
    private readonly CargoEventSource cargo;
    private readonly MissionListenableEventBridge bridge;

    public MissionObjectiveTrackerFactory(
        ShipFlowEventSource shipFlow,
        CargoEventSource cargo,
        MissionListenableEventBridge bridge)
    {
        this.shipFlow = shipFlow;
        this.cargo = cargo;
        this.bridge = bridge;
    }

    public IMissionObjectiveTracker Create(MissionObjectiveType type) => type switch
    {
        MissionObjectiveType.KillEnemies => new KillEnemiesTracker(shipFlow),
        MissionObjectiveType.CollectCargo => new CollectCargoTracker(cargo),
        MissionObjectiveType.ReachDestination => new ReachDestinationTracker(shipFlow),
        MissionObjectiveType.SurviveDays => new SurviveDaysTracker(shipFlow),
        MissionObjectiveType.ListenEvent => new ListenEventTracker(bridge),
        _ => null
    };
}
```

追踪器构造注入事件源的示例（`Start` 协议保持「只订阅 + 判定」，事件源已在构造期就位）：

```csharp
public sealed class KillEnemiesTracker : IMissionObjectiveTracker
{
    private readonly ShipFlowEventSource shipFlow;
    private Action<ShipDestroyedEvent> handler;
    private Action<MissionObjectiveReport> report;

    public KillEnemiesTracker(ShipFlowEventSource shipFlow) { this.shipFlow = shipFlow; }

    public MissionObjectiveType Type => MissionObjectiveType.KillEnemies;

    public void Start(MissionEnding ending, Action<MissionObjectiveReport> report)
    {
        this.report = report;
        handler = eventData =>
        {
            if (eventData.Ship != null && eventData.Ship.Faction == ShipFaction.Enemy)
                report(new MissionObjectiveReport { Increment = 1 });
        };
        shipFlow.ShipDestroyed += handler;
    }

    public void Stop()
    {
        if (shipFlow != null && handler != null) shipFlow.ShipDestroyed -= handler;
        handler = null;
    }
}
```

**注入边界**（对齐事件-订阅规范）：
- 追踪器构造时接收事件源，属「场景装配期依赖注入」例外（工厂在装配期持有事件源显式引用）；
- 任务链模块 `MissionService` 只依赖 `IMissionObjectiveTrackerFactory` 窄接口，**不持有任何事件源引用、不感知追踪器构造细节**；
- 工厂在 `MissionSystem` 装配时创建（§5.3），`MissionService` 经构造注入工厂。

**两类追踪器的生命周期**：

| 类型 | 创建者 | 生命周期 | 进度去向 |
|------|--------|----------|----------|
| 任务级追踪器 | `MissionService`（接取/进入结局判定时） | 任务进行中，收尾时销毁 | 非 `unique` 结局的任务级进度 |
| 全局追踪器 | `MissionGlobalProgressHost`（常驻宿主，§5.8） | 跨场景常驻 | `unique` 结局的全局计数器 |

### 5.6 统一上报契约

追踪器与进度持有方之间通过**回调上报**（`Action<MissionObjectiveReport>`）而非全局事件解耦；任务链模块对外广播的是**任务级**事实（`MissionProgressChangedEvent` / `MissionEndedEvent` 等），供 UI / 音频 / 特效订阅。

| 通信 | 形式 | 说明 |
|---|---|---|
| 事件源 → 追踪器（构造注入） | 依赖注入（装配期） | `MissionObjectiveTrackerFactory` 构造追踪器时注入 `ShipFlowEventSource` / `CargoEventSource`（§5.5.2） |
| 领域事件 → 追踪器/桥 | 事件订阅 | 追踪器订阅 `ShipFlowEventSource` / `CargoEventSource` 等；桥把白名单枚举映射到这些订阅 |
| 追踪器/触发判定 → 桥 | Callback（`Subscribe`/`Unsubscribe`） | `ListenEventTracker` 与 `IsTriggerSatisfied` 经桥订阅，不直接碰事件源 |
| 追踪器 → 进度持有方 | Callback（`Action<MissionObjectiveReport>`） | 注入回调，上报增量/绝对值/达成 |
| 外部系统 → 任务系统（接取） | 事件广播 | `MissionAcceptRequested`：任意系统请求接取 |
| 任务链模块 → 奖励模块 | 事件广播 | `MissionEndedEvent`：结局达成，奖励模块订阅后派发 |
| 奖励模块 → 经济系统 | Command（`TryAdd`） | 转账需同步返回值/失败结果，允许直接调用（事件-订阅规范的例外） |
| 任务链/奖励模块 → 外部 | 事件广播 | `MissionAccepted` / `MissionProgressChangedEvent` / `MissionEndedEvent` / `MissionRewardGranted` 等任务级事实 |

**`unique` 结局的判定路径**：

1. 全局追踪器常驻监听事件，事件发生时写全局计数器（`progressId` 对应 `globalProgressId`）；
2. 任务进入 `InProgress` 时，读取全局计数器当前值作为该结局进度；
3. 计数器值 ≥ `targetValue` → 结局立即达成；未达时，后续全局计数器增长触发任务链模块重新判定；
4. 计数器满后不重置，配合任务状态实现「一存档只完成一次」。

> 设计动机：领域事件（`ShipDestroyedEvent` 等）是强类型 `readonly struct`，追踪器订阅它们做判定；追踪器上报用 `readonly struct MissionObjectiveReport` 规范化收口，任务链模块因此只需理解一种上报结构，不随目标类型增长而膨胀。

### 5.7 奖励派发模块（奖励外置）

奖励发放从任务链模块**外置**，由独立的奖励派发模块承担——与「进度判定外置到追踪器」对称：任务链模块只做「状态机 + 结局判定」，既不碰进度判定，也不碰经济转账。

```csharp
// 文件：Scripts/Gameplay/Mission/Rewards/MissionRewardDispatcher.cs
// 命名空间：Spaceship.Gameplay

/// <summary>
/// 奖励派发模块：订阅 MissionEndedEvent，读取达成结局的 rewards 并执行发放。
/// 只做「结局 → 奖励 → 转账」的派发，不参与任务状态机。
/// </summary>
public sealed class MissionRewardDispatcher
{
    // 场景装配期注入（依赖注入例外）
    public void Wire(CoinManager coins, MissionEventSource missionEvents);

    // 收到 MissionEndedEvent 后：查 Mission 对应结局的 rewards，逐条转账，再广播 MissionRewardGrantedEvent
}
```

**数据流**：

```
任务链模块（结局达成）
  └─▶ MissionEndedEvent（Mission + endingId + endingKind）
        └─▶ MissionRewardDispatcher 订阅
              ├─ 查 mission.endings[endingId].rewards
              ├─ 逐条转账（金币 → coins.TryAdd，Command 例外）
              └─▶ MissionRewardGrantedEvent（实际发放明细）─▶ UI 展示到账
```

**职责边界**：
- 任务链模块：广播 `MissionEndedEvent`（事实），**不发放、不感知奖励派发者**；
- 奖励派发模块：订阅事件 → 查该结局 `rewards` → 转账 → 广播 `MissionRewardGrantedEvent`（实际发放明细）；
- **转账走 Command**：`coins.TryAdd` 需同步返回「是否成功」且有失败要求，属事件-订阅规范的「必须立即执行、有失败结果要求」例外，允许奖励模块直接调用经济系统；
- **依赖注入**：`CoinManager` / `MissionEventSource` 在场景装配期注入（`[SerializeField]` 或 `Wire`），属「场景装配期依赖注入」例外；
- **失败结局不发正奖励**：奖励模块按结局 `endingKind` 判断，`Failure` 结局通常 `rewards` 为空（§3.5 校验已建议），无正奖励可发。

**扩展点**：未来新增奖励类型（`Item` / `Module`，当前为预留枚举）时，只需在奖励模块内加对应转账分支，任务链框架与数据模型无需改动。

### 5.8 跨场景常驻组件与全局进度宿主

#### 5.8.1 通用模式：跨场景常驻组件

某些运行时状态（全局进度计数器、常驻事件监听等）需要**跨场景连续存在**，不能随场景卸载而销毁。项目采用「每个场景都挂 + 首实例常驻 + 副本自毁」的标准模式：

```csharp
// 文件：Scripts/Core/ScenePersistentSingleton.cs（通用基类，供各模块复用）
// 命名空间：Spaceship.Core

/// <summary>
/// 跨场景常驻组件基类：每个场景都挂一份，首个加载的实例成为常驻单例，
/// 其余场景的副本在初始化前检测到已存在实例即销毁自身。
/// </summary>
public abstract class ScenePersistentSingleton<T> : MonoBehaviour where T : ScenePersistentSingleton<T>
{
    private static T instance;

    public static T Instance => instance;

    protected virtual void Awake()
    {
        if (instance != null && instance != this)
        {
            // 已有常驻实例：本场景的副本自毁，避免重复监听 / 重复计数
            Destroy(gameObject);
            return;
        }
        instance = (T)this;
        DontDestroyOnLoad(gameObject);
        OnPersistentInitialized();
    }

    /// <summary>成为常驻实例后的初始化入口（子类覆写）。</summary>
    protected abstract void OnPersistentInitialized();

    protected virtual void OnDestroy()
    {
        if (instance == this) instance = null;
    }
}
```

**模式要点**：

1. **每个场景都挂**：无论从哪个场景启动，都能第一时间创建常驻实例（不依赖特定入口场景）；
2. **初始化前检查**：`Awake` 内先判 `instance != null`，若已存在则 `Destroy(gameObject)` 并 `return`，**不执行任何初始化**（避免重复订阅 / 重复计数）；
3. **首实例常驻**：`DontDestroyOnLoad` 跨场景保留；
4. **副本自毁**：后加载场景的副本在 `Awake` 即自毁，且销毁发生在初始化之前。

> 适用范围：此模式是通用约定，供后续模块优化审查复用——凡「跨场景连续存在的运行时状态 / 常驻监听」，一律按此模式处理（例如未来若要统一 `GameSaveService` 为常驻、统一事件总线等）。

#### 5.8.2 应用：全局进度宿主 MissionGlobalProgressHost

全局进度计数器（§3.7）与全局追踪器需要跨场景常驻，故落地为常驻组件：

```csharp
// 文件：Scripts/Gameplay/Mission/MissionGlobalProgressHost.cs
// 命名空间：Spaceship.Gameplay

/// <summary>
/// 全局进度宿主：跨场景常驻，持有全局进度计数器并创建/管理全局追踪器。
/// 每个场景都挂一份，首个实例常驻，其余副本自毁。
/// </summary>
public sealed class MissionGlobalProgressHost : ScenePersistentSingleton<MissionGlobalProgressHost>
{
    private readonly List<IMissionObjectiveTracker> globalTrackers = new();

    protected override void OnPersistentInitialized()
    {
        // 根据 MissionDatabase 中所有 unique 结局创建全局追踪器（常驻）
    }

    /// <summary>场景装配器在每场景初始化时调用，把当前场景的事件源重新绑定给常驻宿主。</summary>
    public void Rebind(ShipFlowEventSource flow, CargoEventSource cargo, SaveData data);

    /// <summary>读取指定 progressId 的全局计数器值。</summary>
    public int GetProgress(string progressId);

    /// <summary>向指定 progressId 的全局计数器写入增量（全局追踪器上报时调用）。</summary>
    public void Accumulate(string progressId, int increment);
}
```

**关键点——事件源是场景态，常驻宿主需「重绑定」**：

- 全局追踪器监听 `ShipFlowEventSource` / `CargoEventSource` 等**场景内事件源**，而常驻宿主本身跨场景存活；
- 场景切换后，旧场景的事件源被销毁，常驻宿主的订阅会失效。因此每个场景的 `MissionSystem.EnsureInitialized()` 都调用 `host.Rebind(flow, cargo, data)`：
  - 反订阅旧场景事件源（若存在）；
  - 订阅新场景事件源；
  - 更新对 `SaveData` 的引用（存档服务可能也在新场景重建）；
- 计数器**数值**始终在 `SaveData.globalProgress`（磁盘持久），宿主只负责「监听 + 累加」，不因场景切换丢失计数。

**与 `GameSaveService` 的关系**：当前 `GameSaveService` 仍为场景内挂载（`Awake` 从磁盘 Load）。全局进度宿主通过 `Rebind` 拿到当前场景的 `SaveData` 引用，写回 `globalProgress`；`GameSaveService` 是否也升级为常驻，留待后续模块优化审查（§5.8.1 适用范围）。

## 6. 存档改造

### 6.1 MissionSaveEntry

```csharp
// 旧：任务 ID + 状态 + 当前阶段索引 + 阶段进度
// 新：任务 ID + 状态 + 各非 unique 结局的进度 + 最终达成的结局
[Serializable]
public sealed class MissionSaveEntry
{
    public string missionId;
    public int missionState;
    public List<EndingProgressEntry> endingProgress;   // 非 unique 结局的任务级进度
    public string completedEndingId;                   // 最终达成的结局（Completed 时非空；区分成败 + 供前置判定）
}

[Serializable]
public sealed class EndingProgressEntry
{
    public string endingId;
    public int progress;
}
```

**`completedEndingId` 的必要性**：失败/成功都是 `Completed` 态，若只存状态无法区分成败，也无法支持「前置任务指定结局」的判定。因此任务终结时记录最终达成的 `endingId`：

- 任务 `Completed` 时 `completedEndingId` 非空，指向达成的结局；
- 后续任务 `prerequisites` 含 `endingId` 时，据此判断前置是否满足；
- 失败结局的后续（惩罚/补偿分支）同样依赖此字段。

### 6.2 SaveData

```csharp
// 旧
private List<QuestSaveEntry> questStates = new();
public IReadOnlyList<QuestSaveEntry> QuestStates => questStates;
public void ReplaceQuestStates(IEnumerable<QuestSaveEntry> entries);

// 新
private List<MissionSaveEntry> missionStates = new();
private List<GlobalProgressEntry> globalProgress = new();   // 全局进度计数器（§3.7）

public IReadOnlyList<MissionSaveEntry> MissionStates => missionStates;
public IReadOnlyList<GlobalProgressEntry> GlobalProgress => globalProgress;
public void ReplaceMissionStates(IEnumerable<MissionSaveEntry> entries);
public void ReplaceGlobalProgress(IEnumerable<GlobalProgressEntry> entries);
```

### 6.3 schemaVersion

`schemaVersion` 默认值 **5 → 6**。按《存档版本维护》规则：不做旧档迁移与兼容——旧档缺失 `missionStates` / `globalProgress` 字段即空，任务按初始状态启动，其余数据照常保留。

## 7. 可视化编辑器工具

### 7.1 定位与边界

- **完全独立**，不依赖 SequenceMap（SequenceMap 非本模块负责人维护，禁止改动）。
- 画布直接使用 Unity 原生 `GraphView` API，数据直接操作 `MissionDatabase` 内的 `Mission` 对象。
- 代码全部位于编辑器程序集 `Assets/Scripts/Editor/MissionEditor/`，不污染运行时。

### 7.2 架构

```
MissionGraphWindow : EditorWindow
├── 工具栏：新建任务（含模板）/ 新建任务组 / 导入 JSON / 导出 JSON / 自动布局 / 校验
├── 左侧列表（200px）：任务组归类列表（单击定位 / 双击编辑 / 右键菜单）
├── 中央画布（MissionGraphView : GraphView）
│     ├── MissionNodeView（每个 Mission 一个节点）
│     │     ├── 标题：title + 状态图标
│     │     ├── 摘要：结局列表 + 目标类型标签 + 奖励摘要
│     │     ├── 输入端口（前置）
│     │     └── 输出端口（后续，按结局分支）
│     ├── MissionGroupNodeView（每个 MissionGroup 一个半透明分组区域）
│     └── MissionEndingEdgeView（连线标签：endingId / endingTitle）
└── 右侧详情（280px）：MissionDetailPanel（IMGUI，编辑选中任务的完整字段）
```

### 7.3 节点与连线语义

| 画布元素 | 绑定数据 | 编辑语义 |
|---|---|---|
| `MissionNodeView` | `Mission` 实例 | 双击/右键 → 右侧详情面板编辑 |
| 输入端口 | 该任务的 `prerequisites` | 拖入连线 = 新增前置（含 endingId） |
| 输出端口（每个结局一个） | 该任务的 `endings[].followupMissionIds` | 拖出连线 = 为对应结局新增后续任务 |
| `MissionEndingEdgeView` | 两端任务 + `endingId` | 标签显示结局标题；`Delete` 移除该结局的后继 |
| `MissionGroupNodeView` | `MissionGroup` 实例 | 同 `groupId` 的节点归入其区域 |

**双向同步**：在「结局 X 下加任务 B」= 自动给 B 的 `prerequisites` 写入「A + 结局 X」；给 B 加前置「A 的结局 X」= 自动在 A 的结局 X 下追加 B。两端始终一致。

**约束**：连线禁止自连、禁止成环（尝试时红色高亮并阻止），对应 `MissionDatabase.Validate` 的循环依赖校验。

**可见性样式**：`hidden == true` 的节点在画布上用灰色半透明/虚线边框标记「隐藏」，与正常任务区分；`autoStart == true` 的节点在输入端口旁标记「自动开始」；`endingKind == Failure` 的结局输出端口/连线用红色标记，`Success` 用绿色，`Neutral` 用灰色。

### 7.4 任务模板

编辑器提供「任务模板」，策划新建任务时可选模板快速创建（模板预填一个结局的进度条配置）：

| 预设模板 | 预填内容 |
|---|---|
| 摧毁任务 | `objectiveType = KillEnemies` + 默认目标值 |
| 收集任务 | `objectiveType = CollectCargo` + 默认货物类别 |
| 到达任务 | `objectiveType = ReachDestination` + 默认目的地 |
| 存活任务 | `objectiveType = SurviveDays` + 默认天数 |
| 剧情任务 | `objectiveType = ListenEvent` + 默认 `listenEvent`（枚举下拉选） |
| 隐藏规则 | `hidden = true` + `autoStart = true` + `unique = true` + `objectiveType = ListenEvent`（后台计数用） |

模板为编辑器层预设（代码预设或模板配置资产），可扩展；扩展新目标类型时同步补一个模板。
